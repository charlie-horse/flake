# c4130: GPU inference host

c4130 is one of the three NixOS 26.05 servers (c4130, r440, m2mini) that run the cluster. Besides its etcd member, control plane and kubelet ([cluster runbook](../cluster.md)), it runs vLLM and LMCache on two V100s ([c4130-vllm.md](c4130-vllm.md)).

Config: `hosts/c4130/`, built through `lib.system.x86_64-linux.mkServer` (`parts/hosts.nix`, `lib/system/mkServer.nix`), so it gets only its host dir plus `modules/cluster` and `modules/server`.

| File | What it holds |
|---|---|
| `hosts/c4130/default.nix` | import list (order matters for byte-identical output; keep it) |
| `hosts/c4130/configuration.nix` | base system, firewall, Tailscale prefs, md RAID event logging, `legacyCharlie` switch |
| `hosts/c4130/hardware-configuration.nix` | RAID, filesystems, NVIDIA driver, container toolkit |
| `hosts/c4130/vllm/default.nix` | host values for the vLLM / LMCache modules from input `vllm-fork` ([c4130-vllm.md](c4130-vllm.md)) |
| `hosts/c4130/builder.nix` | remote builds on r440 over bond0 ([build-cache.md](../build-cache.md)) |
| `hosts/c4130/gpu-window.nix` | the nightly GPU window ([below](#gpu-window)) |

## Hardware
- 2× Tesla V100-PCIe-32GB, both sm_70, on the same PCIe switch with no NVLink. Driver branch 580, the last one for Volta (`hardware.nvidia.datacenter.enable`, proprietary module, `open = false`; fabricmanager forced off, no NVSwitch).
  > **Unverified:** the 580 branch is not named in the repo; it comes from the datacenter driver nixpkgs selects. Check with `nvidia-smi` on the host.
- 48 threads, 125 GB RAM, no swap (`swapDevices = [ ]`).
- Root: ext4 `C4130-ROOT` on SATA SSD md RAID1 (`/dev/md/local_store`). There is no MTA, so md events (Fail, DegradedArray, …) go to the journal: `journalctl -t mdadm`.
- In Kubernetes the node is tainted `nvidia.com/gpu=vllm:NoSchedule` and labelled `nvidia.com/gpu.present=true`; only workloads that tolerate the taint (one-per-node ones) land there. The GPUs belong to `vllm.service` ([c4130-vllm.md](c4130-vllm.md#vllmservice-owns-the-gpus)).

### CUDA and Volta constraints
- **CUDA 13 can't target sm_70.** Anything that compiles or ships GPU kernels must use CUDA 12.x: vllm-sm70 (what runs since 2026-11-12) uses CUDA 12.6 with torch 2.14.0+cu126; the old fork, still used for the Flint checkpoint recipe, used 12.8 with torch 2.10.0+cu128.
  > **Unverified:** the vllm-sm70 CUDA/torch versions are in that repo, not this one.
- No bf16 on Volta: run everything as `--dtype half` (the vLLM module adds it for every model).
- PyPI ships only CUDA 13 LMCache wheels, so LMCache is built from source against CUDA 12 ([c4130-vllm.md](c4130-vllm.md#lmcache)).

## Network
- LAN `eno1` at `10.0.0.95`; Tailscale advertises exit node + `10.0.1.0/24`, tag `tag:node` (`server.tailscale`, `modules/server/tailscale.nix`).
- Open globally: TCP 22, 80, 443. Cluster ports are opened by `modules/cluster` to the cluster nodes only.
- vLLM API 8000 on `eno1` + `tailscale0`, and on `bond0` from r440 (`10.25.0.2`) only (`builder.nix`). LMCache dashboard 8081 on `eno1` + `tailscale0`. Neither has authentication; the user relies on network policy.
- Direct 2×25G link to r440: LACP `bond0`, c4130 `10.25.0.1/30` (details: [build-cache.md](../build-cache.md)).

## Accounts and access
Access from a cloud session (Tailscale, SSH, who runs `sudo`) is in the [cluster runbook](../cluster.md); accounts and sudo policy in [auth.md](../auth.md). On c4130:
- Stage 2 of charlie's removal is set in config (`custom.server.legacyCharlie.enable = false;` in `configuration.nix`): `admin` is the only login, and `/etc/nixos` belongs to admin:root.
  > **Unverified:** whether c4130 has already switched to that generation is host state. Check with `getent passwd admin charlie`; on a host still in stage 1, use `charlie` and `~charlie` wherever this doc says `admin` / `~admin`.
- `git pull` and `nixos-rebuild build` in `/etc/nixos` need no sudo as its owner; `nixos-rebuild switch`, `journalctl -u vllm` and `systemctl stop/restart` do. Never `sudo git` there.

## Deploying c4130
Every change, including a model entry or a `vllm-fork` re-lock, goes through this repo: branch, CI, merge (general rules: [cluster runbook](../cluster.md)). Then, as admin on c4130, **outside the GPU window**:

```sh
# 1. GC first (Charlie's rule)
sudo nix-env -p /nix/var/nix/profiles/system --delete-generations +2 && sudo nix-collect-garbage
# 2. pull and build (no sudo; the build itself runs on r440)
cd /etc/nixos && git pull && nixos-rebuild build --flake /etc/nixos#c4130
# 3. optional, around risky starts: the RAM guard (see below)
# 4. switch
sudo nixos-rebuild switch --flake /etc/nixos#c4130
```

- **GC before every switch.** After a switch that replaces the Flint checkpoint, also GC the old ~23 GB checkpoint path.
  > **Unverified:** root disk usage is host state. Recorded: ~41% (207 GB free) on 2026-11-05, 60% on 2026-11-12. Check with `df -h /` before the switch.
- **Outside 22:00–05:55 America/New_York.** A switch (or reboot) inside the window starts `vllm.service` again and takes the GPUs from whoever is using them.
- `switch` exiting with status 4 means a unit failed: read `systemctl --failed`. etcd runs here too: switch one host at a time and run the etcd health check from the [cluster runbook](../cluster.md) afterwards.
- Never run `nix flake update` or edit files in `/etc/nixos` on the host.
- What c4130 runs: `nix-store -qd /run/current-system` and `git -C /etc/nixos log -1`. The deployed `vllm-fork` commit is the one in `flake.lock` at that commit; `main` may be ahead.
- Watch a vLLM start with `journalctl _SYSTEMD_INVOCATION_ID=$(systemctl show -p InvocationID --value vllm)` (3–6 min; the first start of a new model also JIT-compiles kernels). Look for "Application startup complete" or a Traceback.
- **RAM guard.** `~admin/archive/notes/flint-nix/ramguard.sh` stops vllm and LMCache if MemAvailable drops under 6 GB (runs ~25 min): `sudo systemd-run --unit=ramguard --collect ~admin/archive/notes/flint-nix/ramguard.sh`. Use it around risky starts (new model, bigger L1, fork bump).

### Builds
c4130 builds nothing itself (`nix.settings.max-jobs = 0`): every derivation goes to r440, and substitutes come from `https://cache.neuros.is`. Builder, cache, concurrency limits and the bond0 link: [build-cache.md](../build-cache.md).

If r440 is down, build locally with `--option max-jobs 4`, and **stop LMCache first**: with a model and LMCache running only ~16–18 GB of RAM is free, while the Flint checkpoint conversion peaks at ~25 GB and a CUDA tree runs 16 nvcc jobs.

## GPU window
`gpu-window.nix` lends both V100s to the login users every night:

| Timer (America/New_York) | Unit | Does |
|---|---|---|
| 22:00 | `gpu-window-start` | `systemctl stop vllm.service`, nothing else |
| 05:55 | `gpu-window-end` | kills the GPU processes of the login users (SIGTERM, SIGKILL after 15 s), then starts `vllm.service`; 06:00 is the deadline |

- Login users: `admin`, plus `charlie` while `custom.server.legacyCharlie.enable` is on.
- Only processes in the user's own `user-<uid>.slice` (login session, tmux, user service) are killed. A GPU pod that kubelet runs under the same uid sits in a kubepods cgroup and is only logged as skipped.
- Both are oneshots run by timers with `Persistent = false`: a run missed while the host was down is not replayed at boot. A failure shows in `systemctl --failed`. Nothing here touches the Kubernetes services.
- `vllm-lmcache.service` stays up overnight (about 328 MiB per GPU and the 64 GB pinned L1 stay allocated).
- The timers don't track window state: a `nixos-rebuild switch` or reboot between 22:00 and 06:00 starts `vllm.service` (it is enabled). Stop it again by hand, or switch outside the window.
- During the day, a GPU job outside the service must stop `vllm` first ([c4130-vllm.md](c4130-vllm.md#vllmservice-owns-the-gpus)).

## Operational gotchas
- **pgrep over SSH.** `pgrep -f <pattern>` matches its own `bash -c` command line; use `ps -ef | grep '[x]yz'`.
- **Stopping vllm.** `Restart=on-failure` brings it back after a kill: `sudo systemctl kill --signal=SIGKILL vllm && sudo systemctl stop vllm`.
- **`nixos-rebuild build` writes `./result`**; use `nix build --no-link` when you only need to know it builds and don't want to clobber `~/result`.
